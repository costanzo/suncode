# Runtime Phase 1

SunCode's runtime is an embedded Rust SDK owning provider integration, agent turns, policy, SQLite state, approvals, checkpoints, credentials, and the client-facing native SDK surface. It has no standalone server or client-facing HTTP/SSE adapter.

The runtime persists durable history and per-turn provider-reported token usage in SQLite, keeps streaming deltas ephemeral, and exposes named methods, session usage aggregates, snapshots, and ordered direct subscriptions to its host process.

The Rust `suncode-db` package in `runtime/crates/db` owns SQLite persistence DTOs, store operations, and initialization of one current 14-table schema from an ordered manifest of table-owned SQL files plus provider/model seed data. The runtime core consumes it as a library dependency. It has no schema versions or general migration metadata and rejects incompatible databases without conversion; initialization can transactionally add the empty dependency table to an otherwise-current 13-table database. `project` is the project identity table, and `project_dependency` stores registered read-only source roots. `session` is the conversation root; `session_turn` owns turn admission, lifecycle, cumulative usage, and approval recovery; `session_call` owns each LLM request and its provider-reported usage; `session_tool_use` exclusively owns tool request/result state; and `session_message` owns timestamp-ordered user, assistant, and thinking content without duplicate usage. Provider context derives transient tool-role messages from succeeded tool-use rows rather than duplicating them in `session_message`. `configuration` stores global/project/session overlays and seeds global logging level, directory, size, and retention policy. Rust applies those settings before normal runtime logging; Avalonia reads them through the SDK and writes its own log file. Provider rows declare a known adapter, currently `openai` for OpenAI-compatible built-in and custom endpoints. Runtime events are live-only; lagged clients reload normalized snapshots.

The Rust `suncode-llm` package owns provider-neutral completion contracts, owned model metadata, model routing, built-in provider construction, OpenAI-compatible HTTP/SSE handling, and public custom provider registration. It has no database dependency. Core injects provider credentials through `ApiKeyResolver`, supplies tool schemas per request, and converts persistent messages and completion results at the agent boundary. Trusted enterprise callers can register an in-process trait implementation or reuse the OpenAI-compatible adapter with a custom endpoint, then inject it while constructing `RuntimeSdk`. The database can persist custom OpenAI-compatible provider and model rows; desktop catalog CRUD/API and dynamic provider plugins are not implemented.

The SDK exposes bounded, read-only Git status and per-file diff methods backed by the audited operations crate. Repository discovery, project-relative path filtering, diff parsing, and output bounds remain Rust-owned; the client receives typed DTOs only.

The Avalonia project window also exposes a left-gutter Explorer that lazily lists the opened project and a `Dependencies` group. Users can add or remove folder registrations; removal never changes source files. Rust returns shallow bounded directory DTOs and omits symlinks. The agent receives dependency IDs and display names, reads them through `dependency:<id>/...` aliases with `read`, `glob`, or `grep`, and cannot write, execute, inspect Git, checkpoint, or undo against those roots.

Process execution is split between a structured `process` tool, which passes one program and explicit argv without shell parsing, and an OpenCode-compatible `bash` tool with `command`, optional millisecond `timeout` (maximum 600000), and optional `workdir`. Bash uses Windows PowerShell on Windows and POSIX `sh` on macOS/Linux. Historical `shell`/`script` calls remain readable through an internal compatibility path but are not advertised to new model requests. Recoverable invalid or malformed tool arguments are returned as tool errors to the model so it can regenerate the call within the same turn; authorization and runtime failures remain terminal. Output streams are continuously drained, previews are bounded to a rolling tail, and oversized output is retained in a complete artifact. Turn cancellation terminates the Unix process group or Windows process tree before returning. Windows child processes use `CREATE_NO_WINDOW` so the desktop does not flash a console window. Both require process-execution approval, retain project-scoped working directories and filtered environments, and report stable executable, permission, working-directory, or generic start failures. The provider prompt includes ephemeral host platform and local-time context so the model selects the correct shell dialect and does not need a process merely to discover the current date.

The existing provider trace SDK methods expose a turn/call hierarchy for one session and detailed normalized messages, tool uses, request/response data, timing, token usage, nullable cache usage, and independently nullable provider HTTP request/response-object IDs for one call. Turns without model calls remain visible. Trace DTOs exclude credentials, authorization headers, and raw provider wire payloads.

The seeded provider catalog includes six providers with two models each: DeepSeek (`deepseek-v4-flash`, `deepseek-v4-pro`), Zhipu GLM (`glm-5.2`, `glm-5.3`), OpenAI (`gpt-5.5`, `gpt-5.6-sol`), Kimi (`kimi-k2.7-code`, `kimi-k3`), Claude (`claude-sonnet-5`, `claude-opus-5`), and Gemini (`gemini-3.5`, `gemini-3.6-flash`). Provider credentials and endpoints are stored on `llm_model_provider`; model request codes, context limits, auto-compaction thresholds, output limits, and capabilities are stored on `llm_model`. Provider endpoint/model environment overrides are not used.
