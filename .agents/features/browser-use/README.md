# Browser Use and Embedded Preview

**Status.** Browser Use and on-demand Chromium installation are implemented and focused-tested. The current Windows x64 CEF component has passed an isolated native-host check through package verification, activation, subprocess startup, Rust CDP, and screenshot capture. Normal installed-desktop conformance remains unverified. Embedded preview is partially implemented.

These are two separate capabilities. Each has its own profile, and they do not share state.

The managed CEF binding, browser views, runtime host and component installer all live under `apps/desktop-avalonia/`. Desktop calls its built-in binding directly and initializes native CEF on demand. `Costanzo.CefGlue.Avalonia` 1.0.0-preview.1 and `CefGlue.Next.Common` 152.7977.831 bind to CEF 152.0.6. Native Chromium is downloaded separately through Browser use Settings. The trusted Desktop catalog pins package identities and SHA-256 digests for Windows x64/ARM64 and Linux x64/ARM64. macOS reports unsupported because the current binding cannot activate a framework outside the signed application bundle.

## Chromium component installation

- The Avalonia `BrowserUseSettingsControl.axaml` and `BrowserRuntimeViewModel.Component.cs` implement download, repair, uninstall, download cancellation, explicit installed-file verification, source selection, and restart using the shared Settings controls. Enablement is independent of installation. The shared application setting also gates built-in browser entry points across project windows. Disabling closes browser/preview views, collapses their panels, and hides the right gutter plus native and compact View-menu commands. Re-enabling restores the entries and allows the user to open a panel explicitly. These operations are user initiated. Browser tools and first-use recovery never download components automatically. The design-system route `#/projects/desktop/settings/browser` remains an illustrative simulation of this flow.
- NuGet.org and Huawei Cloud (China) share the same immutable compatible package version and expected SHA-256 from the trusted catalog. The complete package digest is checked before extraction. A missing source version, interrupted download, or mismatched digest remains a distinct error with retry or source switching. With the SDK available, downloads use its trusted-host proxy configuration. Explicit installation also works without the SDK using the system proxy. Both paths enforce strict TLS certificate verification even when the agent's certificate preference is disabled.
- Desktop owns the source preference in `browser-components/source.json` beneath its application data directory. Installation prepares files under `.staging-<GUID>`, writes `installation.json` with target, version, package digest, and per-file hashes and sizes, moves the component into `installed/<GUID>`, and atomically replaces `active.json`. Failed or canceled replacement preserves the previous active component. Temporary staging and uncommitted destinations are cleaned. Successful repair removes inactive installations that have not been loaded in the process. A loaded previous runtime is retained until restart; primary Desktop startup then collects it after acquiring the data-directory instance lock and installer lock. CEF subprocesses never run this cleanup. One service owns operations across Settings and project windows, and closing Settings leaves an installation running.
- Full installed-file SHA-256 verification runs before native loading and on explicit verification. Lightweight availability checks validate the installation manifest against the catalog and check file existence and size. Avalonia performs these component checks through the existing Browser Host page-preparation request, including requests preceding cached CDP operations. Missing, incompatible, installing, restart-required, unsupported, and corrupt remain Desktop-owned component states. Rust and the SDK bindings carry only the existing host-ready result and CDP connection/operation state.
- Missing components fail Desktop page preparation and lead to Browser use Settings. The Settings navigation entry remains visible and selectable while disabled or missing Chromium, preserving access to enablement and component management. Tool advertisement depends on global enablement and the host capability ceiling. Repair and explicit verification require all project browser and built-in preview views to stop. Replacing a component already loaded in the process retains those files and requires an application restart. The restart confirmation explains that active turns must finish or be stopped first.
- Installation preserves the runtime package's top-level `LICENSE.txt` and includes it in the per-file hash manifest. Managed CEF third-party notices are included in build and publish output as `browser-third-party-notices.txt`.
- Uninstall requires the shared destructive confirmation and zero active browser/preview views. Under the existing installer lock it writes `uninstall.pending`, removes managed `installed/<GUID>` payloads and `.staging-<GUID>` temporary packages, then deletes the activation pointer and pending marker. Saved browser data and the source preference remain. Loaded native files require restart; primary Desktop startup completes pending removal before CEF can start. A partial deletion preserves the marker and exposes retry. Installation and verification remain blocked while removal is pending. Successful removal returns to the missing/download state and permits explicit reinstallation.

### Verification limits

Focused verification passed 17 Rust browser tests, five real-Chromium lifecycle/operation regressions including cached-session host requests, and 35 focused C# cases covering component installation/layout, the existing Browser Host bridge, shared application settings, and browser entry visibility across windows. The visibility cases verify native and compact menus plus the actual Avalonia gutter binding at default/minimum sizes in both themes and languages. Repair regression coverage verifies obsolete-directory cleanup, loaded-runtime retention until restart, and preservation when the active installation is invalid. Uninstall coverage verifies confirmation, immediate removal, loaded-runtime retention until restart, recovery after partial deletion, reinstall, retained data/source preference, and the actual localized Settings actions. The component cases include malformed-manifest handling and SDK-independent explicit installation and removal. The isolated Windows x64 host used the real repository-signed NuGet package and exercised SHA-256 verification, extraction, activation, CEF subprocess startup, Rust CDP, and a real screenshot. After consolidation into Desktop, its built-in binding passed the native CDP/screenshot regression again. A fresh publish includes normal managed CEF dependencies and browser notices, with no separate browser assembly, plugin directory, or Chromium payload.

Actual Avalonia production-control Skia headless renders cover light and dark themes in `.impeccable/review/browser-production-light.png` and `.impeccable/review/browser-production-dark.png`. Native screen capture timed out, so window-manager visual verification remains pending. Linux and ARM64 native conformance have not run. The full Desktop test project is blocked by existing ChangedPaths, session, and review compilation failures. Normal Desktop smoke startup is blocked by an existing database schema mismatch. These checks leave normal installed-desktop conformance unverified.

## Browser Use (CEF CDP)

The Rust `suncode-browser` client uses `chromiumoxide` to connect over WebSocket to the CEF remote debugging endpoint configured by the Avalonia client. CEF is not initialized at desktop startup. When an enabled Browser Use tool first executes, Rust asks the Avalonia host to initialize CEF and create a page for that project, then connects to the matching opaque CDP target. The agent owns policy, lifecycle, request timeouts, and artifacts; CEF owns Chromium and UI. `suncode-browser` owns the tool contract (`tools`), per-project runtime (`runtime`), and CDP transport (`cdp`); the agent core only reads the enablement setting and routes `browser_*` calls to `BrowserRuntime`.

- `browser_use_enabled` is global and defaults to `false`. Enabling does not launch or install anything. Browser tools are advertised when enabled and permitted by the host capability ceiling. The first browser call lazily initializes CEF, creates a project-scoped page and connects CDP. Later calls reuse that page after the existing Browser Host request. The Avalonia host checks the component and returns an already initialized page without changing panel visibility or selection. Rust remembers the page's CDP target id, so a reconnect after cancellation, failure, or restart finds the page even after it has navigated away from its initial URL. Disabling retires the tools, cancels calls, and disconnects project sessions while keeping profiles. The host capability ceiling (for example, the CLI) can suppress Browser Use entirely.
- Each project has one persistent profile under the agent data directory. Profiles never live inside the project and never reuse the user's own browser profile. Rust chooses the profile and download paths, and CEF never receives provider credentials. SunCode proxy settings are not applied to CEF; it uses the host's default network configuration.
- Model tools are available only to primary sessions: `browser_open`, `browser_navigate`, `browser_snapshot`, `browser_click`, `browser_fill`, `browser_press`, `browser_screenshot`, `browser_tabs`, and `browser_close_page`. Each project has one page, so tools take no page id. `browser_snapshot` returns the page's visible text and URL; actions return only the page id or URL. `browser_click` and `browser_fill` target the first element matching a structured locator: role plus exact visible text, label text or `aria-label`, placeholder, test id, or exact visible text. `browser_press` sends one key to the focused element. Raw CSS, XPath, scripts, and element references are rejected. Only `http` and `https` navigation is allowed.
- Every browser call, including observation, has `BrowserAccess` risk and needs interactive approval even under Full Control. Non-interactive use is denied. Browser effects on remote systems and on profiles are never part of filesystem undo.
- Screenshots up to 5 MiB are stored as PNG artifacts. The model receives text metadata, not the image.
- The agent always holds control of the page. `take_browser_control` and `return_browser_control` only refresh runtime state, and there is no user lease. Desktop Settings shows runtime identity and health with start, show/take-control, return-control, stop, verify, component-restart, and clear-data controls. Handoff labels and copy still describe the intended exclusive-control design, beyond the runtime's implemented behavior. Clearing data requires a stopped runtime and a confirmation.

Not implemented: an exclusive user control lease, accessibility snapshots with element references, per-page navigation timeouts, per-origin and per-action policy preflight with action-time confirmation categories, screenshot delivery to vision models, scroll/wait/select/console tools, packaged offline smoke tests on Windows x64 and Linux x64, and other browser engines.

## Embedded preview (CEF)

The desktop project window can show a CEF Chromium pane beside the chat. The pane uses ordinary browser chrome (tabs, navigation, address entry, reload, and disconnect) while still rendering the local development server that Rust starts and owns. Browser Use pages use the same visible surface when the agent requests the project browser page; the client does not add a separate explanatory banner or preview-only title row.

- Rust `PreviewManager` exposes `preview_state`, `start_preview`, and `stop_preview` through the Rust, C, and C# SDKs. Preview configuration lives in project-only settings: `preview_program`, `preview_args`, `preview_cwd`, and `preview_url`. The desktop defaults to `npm run dev` at `http://127.0.0.1:5173/`.
- The server starts as a structured background process with a filtered environment and `HOST=127.0.0.1`. Its working directory is project-scoped, and its process group is cleaned up on stop, project close, and SDK shutdown. The start is a user action, not a model tool call, so no approval prompt is involved.
- Only `http://localhost` and `http://127.0.0.1` URLs without credentials are accepted. Readiness means the port accepts connections within 30 seconds. If the process exits early or never listens, start fails with `preview_server_exited` or `preview_server_not_ready`.
- Preview start, refresh, and stop failures are logged and shown as presentation errors; they do not change the desktop agent connection state or disable otherwise available conversation controls.
- Live refresh works by polling. Rust bumps `reload_generation` when a bounded scan of project file sizes and modification times changes, ignoring `.git`, `node_modules`, `bin`, `obj`, and `target`. The pane reloads when the generation changes. The CEF pane blocks popups, uses an isolated per-project request context, and offers reload and close. It uses the built-in CEF binding and the same installed Chromium component as Browser Use, with a separate profile.

Remaining work includes native HMR event transport, typed preview events (state is polled), normal installed-desktop smoke tests, and Linux/ARM64 native component conformance. macOS external-framework activation requires a binding change.
