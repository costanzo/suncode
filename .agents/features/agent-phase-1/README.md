# Agent Phase 1

The built-in file tools now apply bounded line continuation, ignore-aware glob traversal, and preconditioned BOM/line-ending-preserving edits. Failed shell exits, timeouts, and cancellation remain visible as failed tool operations while retaining structured output.

SunCode's agent is an embedded Rust SDK owning provider integration, agent turns, policy, SQLite state, approvals, checkpoints, credentials, and the client-facing native SDK surface. It has no standalone server or client-facing HTTP/SSE adapter.

The agent persists durable history and per-turn provider-reported token usage in SQLite, keeps streaming deltas ephemeral, and exposes named methods, session usage aggregates, snapshots, and ordered direct subscriptions to its host process. Terminal failure persistence retains structured `error_json` and `error_code` even when the failed state event is projected first, while completed, cancelled, and interrupted outcomes remain protected.

The Rust `suncode-db` package in `agent/crates/db` owns Diesel-backed SQLite persistence DTOs, table-oriented operation modules, and initialization of one current 15-table schema from an ordered manifest of table-owned SQL files plus provider/model seed data. The agent core consumes it as a library dependency. It has no schema versions or general migration metadata and rejects incompatible databases without conversion; initialization can transactionally add the empty dependency table to an otherwise-current 13-table database. `project` is the project identity table, and `project_dependency` stores registered read-only source roots. `session` is the conversation root; `session_turn` owns turn admission, lifecycle, cumulative usage, and approval recovery; `session_turn_todo` owns the authoritative current todo projection for each turn; `session_call` owns each LLM request and its provider-reported usage; `session_tool_use` exclusively owns tool request/result state; and `session_message` owns timestamp-ordered user, assistant, and thinking content without duplicate usage. Provider context derives transient tool-role messages from succeeded tool-use rows rather than duplicating them in `session_message`. `configuration` stores global/project/session overlays and seeds global logging level, directory, size, and retention policy. Rust applies those settings before normal agent logging; Avalonia reads them through the SDK and writes its own log file. Provider rows declare a known adapter, currently `openai` for OpenAI-compatible built-in and custom endpoints. Agent events are live-only; lagged clients reload normalized snapshots.

The Rust `suncode-llm` package owns provider-neutral completion contracts, owned model metadata, model routing, built-in provider construction, OpenAI-compatible HTTP/SSE handling, and public custom provider registration. It normalizes nested and compatible top-level cache-read, cache-miss, cache-write, and reasoning-token usage into nullable provider-neutral fields. It has no database dependency. Core injects provider credentials through `ApiKeyResolver`, supplies tool schemas per request, and converts persistent messages and completion results at the agent boundary. Trusted enterprise callers can register an in-process trait implementation or reuse the OpenAI-compatible adapter with a custom endpoint, then inject it while constructing `AgentSdk`. The database can persist custom OpenAI-compatible provider and model rows; desktop catalog CRUD/API and dynamic provider plugins are not implemented.

Each turn snapshots the project's `tool_call_limit`, which defaults to 64 and accepts values from 1 through 256. An over-budget provider batch is retained as failed tool requests without authorizing or executing any member of the batch.

The SDK exposes bounded, read-only Git status and per-file diff methods backed by the audited operations crate. Repository discovery, project-relative path filtering, diff parsing, and output bounds remain Rust-owned; the client receives typed DTOs only.

The Avalonia project window also exposes a left-gutter Explorer that lazily lists the opened project and a `Dependencies` group. Users can add or remove folder registrations; removal never changes source files. Rust returns shallow bounded directory DTOs and omits symlinks. The agent receives dependency IDs and display names, reads them through `dependency:<id>/...` aliases with `read`, `glob`, or `grep`, and cannot write, execute, inspect Git, checkpoint, or undo against those roots.

The Rust agent automatically loads a non-empty project-root `AGENTS.md` into every provider request as system context. Successful reads of project files discover more specific `AGENTS.md` files between the file directory and project root, attach unseen instructions nearest-first to the normalized read result, and deduplicate them for the current turn. Automatic instruction loading is canonical-project-scoped, bounded to 32 KiB per file, 16 nested files, and 64 KiB per read; it ignores unavailable, invalid, oversized, dependency-owned, and out-of-scope files without failing the turn.

The model receives nine built-in tools: `read`, `glob`, `grep`, `question`, `todowrite`, `write`, `edit`, `bash`, and `webfetch`. The OpenCode-compatible `question` tool pauses the turn with one to eight structured prompts, supports single or multiple choice and optional custom text, and resumes later sibling calls after the client replies or skips. The OpenCode-compatible `todowrite` tool replaces the current turn's todo list, validates up to 100 prioritized items with at most one `in_progress` item, emits `todo.updated`, stores authoritative progress in `session_turn_todo`, and returns the complete list to the model. Its tool-use result remains call history, not the current progress source. The OpenCode-compatible `bash` tool accepts `command`, optional millisecond `timeout` (maximum 600000), and optional `workdir`, using Windows PowerShell on Windows and POSIX `sh` on macOS/Linux. `webfetch` accepts an HTTP(S) URL, optional `text`, `markdown`, or `html` output format (default Markdown), and an optional timeout in seconds (default 30, maximum 120). It requires network approval, rejects embedded URL credentials and cross-origin redirects, accepts at most 5 MiB of textual content, retains output beyond a 64 KiB model preview in a managed artifact, and does not expose binary or image responses. Retired process, patch, shell, and script calls are no longer executable; persisted rows remain readable as history only. Recoverable invalid or malformed tool arguments are returned as tool errors to the model so it can regenerate the call within the same turn; authorization and agent failures remain terminal. Process output streams are continuously drained, previews are bounded to a rolling tail, and oversized output is retained in a complete artifact. Turn cancellation terminates the Unix process group or Windows process tree before returning. Windows child processes use `CREATE_NO_WINDOW` so the desktop does not flash a console window. Process execution requires approval, retains a project-scoped working directory and filtered environment, and reports stable executable, permission, working-directory, or generic start failures. The provider prompt includes host platform and session-start context so the model selects the correct shell dialect while the leading prompt prefix remains stable throughout the session.

Interactive approvals support deny, allow once, and allow for session. Allow for session atomically stores a boolean `full_control` session configuration and resumes the pending call. While enabled, known project-write, process, network, and destructive-write tools skip further interactive approval in that session; argument validation, project/dependency scope, URL validation, auditing, checkpoints, cancellation, and unknown-tool denial remain active. Setting the session value to false restores normal approval behavior.

The existing provider trace SDK methods expose a turn/call hierarchy for one session and detailed normalized messages, tool uses, request/response data, timing, token usage, nullable cache-read, cache-miss, cache-write, and reasoning usage, and independently nullable provider HTTP request/response-object IDs for one call. Turns without model calls remain visible. Trace DTOs exclude credentials, authorization headers, and raw provider wire payloads.

The seeded provider catalog includes six providers with two models each: DeepSeek (`deepseek-v4-flash`, `deepseek-v4-pro`), Zhipu GLM (`glm-5.2`, `glm-5.3`), OpenAI (`gpt-5.5`, `gpt-5.6-sol`), Kimi (`kimi-k2.7-code`, `kimi-k3`), Claude (`claude-sonnet-5`, `claude-opus-5`), and Gemini (`gemini-3.5`, `gemini-3.6-flash`). Provider credentials and endpoints are stored on `llm_model_provider`; model request codes, context limits, auto-compaction thresholds, output limits, and capabilities are stored on `llm_model`. Provider endpoint/model environment overrides are not used.
