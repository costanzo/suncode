# Desktop component updates

Status: C# client implemented and focused-tested; catalog checking is enabled; real package publication, platform signing configuration, and installer integration remain pending.

Avalonia owns one update coordinator under `apps/desktop-avalonia/Infrastructure/Updates/`. Settings → Updates and About → Software updates follow the design-system specimen, including independent component versions, one compatible download plan, localized notes, manual download/restart, automatic checks, progress/cancellation, verification failures, unavailable delivery, and SDK repair. Settings navigation and repair do not require Agent startup. Closing Settings preserves application-owned update work. Without initial-installation receipts, fresh trusted metadata can still show Up to date when actual running Desktop/SDK product versions and ABIs exactly match the recommended pair. This version-only result creates no receipt or installable plan. A differing/unavailable unmanaged runtime instead produces an automatic-installation availability warning, distinct from detected Desktop/state damage. The automatic-check control uses the global Avalonia `sc-toggle-switch` (SCToggle) style without per-page brush overrides.

The client hand-implements the public signed catalog in [`contracts/updates`](../../../contracts/updates/README.md). It verifies Ed25519 over RFC 8785 canonical JSON, bounded metadata, freshness, channel/target, persisted revision high-water marks, exact tested version pairs, ABI identity, and immutable release/archive identities. Checks send no installed versions or user/project identity. Provider insecure-TLS settings never apply to updates.

Downloads are independent full component archives. Verification and extraction precede staging; active component identities remain unchanged until a durable paired-pointer commit. Payload directories are immutable, and the original installation forwards to the selected Desktop. An early C# helper/preflight handshake verifies actual Desktop/SDK identities before Agent database opening. Failure before commit keeps the previous installation; committed activation never assumes an older SDK can safely reopen current data. C# does not access SQLite, add a Rust update API, or perform database rollback.

Transport deadlines cover catalog headers/body (30 seconds), download response headers (30 seconds), no received body data (30 seconds, reset per read), and the complete archive (30 minutes). Timeout/stall failures have distinct localized retry messages and cannot be mistaken for manual cancellation. Failed partial files/staging are cleaned without changing the installed pair; no immediate automatic retry or resume is implemented. Virtual-time tests verify every budget and cancellation precedence.

Focused tests cover the protocol, transport, plans, repair, cancellation, extraction, state durability/barriers, and view models. Real child-process tests confirm valid and invalid native runtime selection before any Agent SQLite startup. Headless layout tests cover both themes, English/Chinese, default/minimum panels, and maximum-length versions.

The checked-in distribution configuration contains the public verification key and the `https://www.suncode.ai` catalog origin with both apex/www download origins; catalog paths use `/updates/v1/{channel}/{target}/latest.json`. Checking is enabled; the canonical origin avoids the apex domain's HTTP 308 redirect. Both current component product versions are `0.1.0`. The website now implements catalog hosting and offline signed publication; its six target files now serve signed 0.1.0 catalogs with First release notes and user-requested sample package values. They have no special status fields; real archives remain absent and a real receipt with different hashes fails immutable-release checks. A release still requires platform identities, signed component packages, deployed catalogs, and a trusted initial installation receipt. Initial-installer integration and installed signed updates on macOS/Windows/Linux remain release verification; local tests and preview images do not establish that those paths are deployed. Packaging and configuration details are in the updater's source README and `website/updates/README.md`.
