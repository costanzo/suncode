# Rust Core Phase 1

## Identifiers and randomness

Rust-generated ids come from `suncode_common::id`: `<prefix>_<26 lowercase Crockford base32 characters>` encoding a UUID v7, so ids are URL- and filename-safe and sort by creation time as strings. Prefixes name the kind: `prj` project, `dep` dependency, `ses` session, `trn` turn, `msg` message, `xch` provider exchange, `apr` approval, `que` question, `ckm` checkpoint manifest, `qmsg` queued message, `sub` subagent invocation, `sbm` internal submission key, `rreq`/`revt` Remote request/event; screenshot artifacts use `browser` and `computer`. Ids are opaque: nothing parses them, and stores keep ids created before this scheme (bare UUIDs) unchanged. Content-addressed ids (tool artifacts, checkpoints, MCP/LSP server ids derived from idempotency keys) are not random and keep their existing formats.

Keys, nonces, and jitter come from `suncode_common::random`, which reads the operating system secure random source and treats its absence as fatal. Remote end-to-end encryption uses a 32-byte random AES-256 key and a fresh random 12-byte AES-GCM nonce per payload.

## Build output

The `agent/` workspace declares every external and internal dependency once in `[workspace.dependencies]`, with package `version` and `edition` in `[workspace.package]`. Member crates use `name.workspace = true` and may only add `features`. Workspace entries carry the version, source, `default-features = false` where needed, and only the features every member requires. Each dependency therefore has a single version across the workspace. All outbound HTTP clients use the shared `suncode-http` crate on that single reqwest version.


The agent, Rust facade, C binding, and CLI keep separate manifests and lockfiles but share the repository-root `target/` through `.cargo/config.toml`. Cargo must run from the repository root or a descendant to discover this configuration; callers outside the repository can pass its path with `--config`. Dev/test profiles retain line-table debug information (`debug = 1`) and Cargo's default incremental compilation. Release profiles remain unchanged. Rust CI pins Rust, rustfmt, and Clippy to 1.98.0 using `RUSTUP_TOOLCHAIN`, overriding the repository's `stable` channel, disables incremental compilation, and caches the shared output; CLI release packaging reads `target/<triple>/release`.

The managed SDK invokes locked Cargo builds with the repository root as the working directory and an explicit shared target directory. Its native-library copy source uses the same directory. `SunCodeCargoTargetDirectory` overrides `CARGO_TARGET_DIR`, which overrides the root `target/` default; relative overrides resolve from the repository root. This changes build placement only, with no SDK or runtime contract change. Changes to shared crates' production dependencies must synchronize the independent `agent`, `sdks/rust`, `sdks/c`, and `apps/cli` lockfiles, including when moving a dependency from dev-only to production use. Validate the C SDK with `--locked` because the Avalonia build enforces that flag; passing agent-workspace tests alone does not validate the desktop dependency graph.

## Source Control ownership

The Rust operations package has no Git implementation or libgit2 dependency. Former `git/status` and `git/diff-file` names fail with `method_unavailable`. Avalonia owns optional read-only system Git inspection; agent process policy, repository ignore rules, checkpoints, and undo remain in Rust.

## Operations

The Rust operations module is provided by the `suncode-tool` package, linked into the runtime, and called in-process.

It enforces canonical project paths, bounded reads and search, preconditioned file mutations, content-addressed file version capture, bounded process execution with filtered environment handling, and bounded approval-gated HTTP(S) text retrieval with same-origin redirect enforcement.

`edit` accepts exact old/new text, either one replacement or a batch against the original file. The forms are mutually exclusive: `path`, `oldString`, `newString`, optional boolean `replaceAll`; or `path`, `edits` with 1-200 objects containing only `oldString` and `newString`. Both forms use the same text field names; `oldText`/`newText` are rejected with guidance to use the canonical names. Unknown fields, mixed forms (including `replaceAll` with `edits`), wrong types, empty old text, and NUL are rejected before policy/approval and checked again during translation. Each old text must match exactly once unless the single-replacement call sets `replaceAll`. Uniqueness counts overlapping occurrences; replace-all selects non-overlapping occurrences. Every batch item resolves against the original file, not preceding replacements' output. Missing, ambiguous, or overlapping batch replacements fail before any file write. No regex, fuzzy matching, or sequential batch semantics are implied.

Matching normalizes LF, CRLF, and CR, then maps selected ranges back to the decoded original. Untouched bytes, UTF-8 BOM, UTF-16LE BOM, and missing final newline are preserved. Within a replacement, corresponding newline positions retain the matched text's endings; added lines use the first matched ending, otherwise the nearest preceding ending, then the following ending, then LF. Mixed endings outside the replacement are never normalized. Text must be valid UTF-8 or BOM-marked UTF-16LE; invalid UTF-16 surrogate sequences, UTF-16BE, legacy encodings, and NUL-containing text fail closed. UTF-16LE output retains its original encoding and retained checkpoint diffs decode it as text.

Edit source and encoded result are each limited to 16 MiB. Source reads use a bounded reader with one extra byte to detect overflow. Each old/new argument and the aggregate expanded replacement text are bounded at 32 MiB. There are at most 10,000 selected ranges; matching stops with a resource error after 10,000 occurrences per item. These limits bound allocation and model feedback rather than allowing a small edit to trigger unbounded whole-file reads. The `write` tool retains its 1 MiB result limit; shared mutation baselines are capped at 16 MiB.

`edit_conflict.details` identifies `reason` (`not_found`, `ambiguous`, `overlap`), zero-based `edit_index` or `edit_indexes`, and a corrective `suggestion`. Match errors include `match_count`, up to eight one-based `candidate_lines`, and `candidates_truncated`. Overlap errors identify the two conflicting items and their start lines. Resource-limit errors may report `match_count_at_least`. Diagnostics do not include arbitrary source snippets or substitute a guessed match.

Successful edits return `source_sha256` (raw pre-edit bytes), `sha256` (raw resulting bytes), `encoding`, `replacement_count`, `changed_count`, `changes`, and `changes_truncated`, in addition to existing path/byte/checkpoint metadata. `changed_count` excludes matched replacements whose effective bytes are unchanged. `changes` contains up to 50 changed ranges, each with its original `edit_index`, one-based old/new start/end line coordinates, and actual `old_text`/`new_text` previews. End coordinates describe the exclusive replacement endpoint, so replacing a newline can end on the next line. Preview text is UTF-8-boundary-safe, capped at 1 KiB per old/new side and 8 KiB combined; each range marks `preview_truncated`. This is a bounded replacement summary, not a complete unified diff; `turn_diff` remains the full retained-change review path.

Edits match current content, so a prior full-file read or model-supplied version remains unnecessary. The agent annotates successful built-in read/write/edit/delete results with `file_observation`, derived from the raw source/result digest. Read observations distinguish `full_read` and `partial_read`; mutations mark `mutation`, while deletion or a read without a whole-source digest invalidates the prior observation. On edit success, `read_state.status` is `unchanged`, `changed`, or `unknown`, comparing the edit's source digest with the latest same-path observation still present in the current conversation. A changed source adds a notice to re-read surrounding content before dependent edits, but an exact, valid edit still succeeds. Retained history/resumption preserves these fields; compacted/missing observations are unknown and are never proof that a file was read. Other sessions, dependencies, MCP/toolset results, and unrelated paths cannot supply the observation. Existing successful-call replay preserves the original notice. Observation hints are not authority grants or write preconditions.

All built-in file mutations share an in-process gate. Edits still compute against their own source before entering the gate; a changed baseline fails the shared precondition. Writes stage a same-directory temporary file, preserve Unix permission bits or the Windows DACL (including protection/inheritance state), sync staged content, store before/after versions, and revalidate containment and exact baseline bytes immediately before publication. Existing files publish by atomic rename; Windows uses `SetFileInformationByHandle(FileRenameInfoEx)` with replace-existing and POSIX semantics so existing readers retain their old complete version. Unsupported filesystems/OS behavior fails without a truncate-and-write fallback. New files use no-clobber publication; racing creators are not overwritten. Deletions share the gate and final baseline check. Ordinary failures clean up the staged file; a process crash can leave an unreferenced staging file. File ownership, extended attributes, alternate streams, hard-link identity, and power-loss durability are not promised by this replacement path. An arbitrary external writer or parent-directory rename can still race the final check: the gate is not an OS sandbox or atomic filesystem compare-and-swap.

`read` returns `sha256` for the complete raw file bytes when reading from line 1 without a line limit and the source fits within 16 MiB. A truncated inline preview still carries the full-file hash when the complete source was read. Line-range reads and sources exceeding that bound omit `sha256`. Bounded-source reads also return `source_sha256` for observation tracking, including line-range reads; this digest does not claim the model saw the whole file. BOM-marked UTF-16LE sources up to 16 MiB are decoded for previews/ranges while hashes always describe the raw source. Larger UTF-8 files retain streaming line-range access with at most 16 MiB selected bytes and no source digest. Existing-file `write` and `delete` require `expected_sha256`, a 64-character hexadecimal digest from `read`, `write`, or `edit`; a stale digest fails with `write_conflict`. Creation requires an omitted or null precondition and refuses to overwrite an existing file. Successful writes and edits return the resulting `sha256` for subsequent mutations. Tool parameters and results use existing JSON storage and add no database schema or compatibility path.

Content search is implemented with embedded ripgrep crates (`ignore`, `globset`, `grep-regex`, and `grep-searcher`). `search/find` uses Rust regular expressions, ripgrep-style standard ignore/hidden-file traversal, project-relative include globs, and a 2 MiB per-file bound. It returns relative paths, one-based byte columns, line previews, and bounded `truncated` results without requiring an external `rg` executable.

`tool/webfetch` accepts textual HTTP(S) responses up to 5 MiB, decodes BOM or declared charsets, and converts HTML to Markdown or plain text through a structured parser. Its model preview is 64 KiB; larger converted output is retained in managed artifact storage. It rejects embedded URL credentials, cross-origin redirects, binary content, and image content.

The model-facing tool registry also includes `question` and `todowrite`. Core validates one to eight prompts with labeled options, pauses the current continuation in the turn recovery snapshot, and emits `question.asked`. The embedded SDK exposes ordered answer and reject calls; answers are validated against option labels, `multiple`, and `custom` before the continuation resumes. `todowrite` validates a complete replacement list of up to 100 prioritized items with at most one `in_progress` item, stores it in the current turn continuation, emits `todo.updated`, and transactionally replaces the authoritative `session_turn_todo` rows. A session snapshot returns `pendingQuestion` while the request is waiting and includes current todos in normalized conversation turns; the tool result in `session_tool_use` is retained as call history only. Restart recovery selects the question continuation path when a resolved question is found in `resuming` state.

Browser Use is implemented by the Rust-owned `suncode-browser` client using `chromiumoxide` against the Avalonia-owned CEF remote debugging endpoint. Rust owns target discovery, request timeouts, policy, lifecycle, artifacts, cancellation, and control ownership; CEF owns Chromium and UI.

Before every provider request, core reloads `<project>/AGENTS.md` as bounded system context. After a successful project file read, it canonicalizes the target, discovers unseen nested `AGENTS.md` files nearest-first up to the project root, and adds them to `repository_instructions` in the normalized tool result. Root instructions are not duplicated in read results; direct instruction-file reads, dependencies, path escapes, non-UTF-8 files, empty files, and files over 32 KiB do not trigger automatic attachment. One read is capped at 16 nested files and 64 KiB of nested instruction content.

Model capability metadata includes `supports_reasoning_effort` and the persisted per-model `reasoning_efforts` catalog, projected as `capabilities.reasoning_effort` and `reasoning_efforts`. `submit_turn` accepts only an effort advertised by the selected model, stores it in the continuation snapshot, and the OpenAI Responses-compatible adapter maps it to the `reasoning.effort` request field.
