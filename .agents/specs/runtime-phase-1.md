# Runtime Phase 1

Tool execution hardening keeps the compact model contracts aligned with audited behavior: `read` applies 1-indexed line ranges before its byte cap, `glob` respects ignore rules, `edit` preserves BOM and line endings while rejecting overlaps, and failed bash exits are represented as failed tool operations with structured status.

The runtime is an embedded Rust SDK inside its host process with one SQLite database under `~/.suncode/data/sqlite/runtime.sqlite3`.

The `suncode-db` Cargo package under `runtime/crates/db` owns the SQLite store, persistence DTOs, current schema resources, and seeded LLM provider/model catalog. The `suncode-runtime` core package consumes it and does not depend on `rusqlite` directly.

The `suncode-llm` Cargo package under `runtime/crates/llm` owns the LLM provider trait, provider-neutral request and response types, model metadata and registry, built-in catalog, and OpenAI-compatible HTTP/SSE adapter. It has no dependency on `suncode-db`, `suncode-runtime`, or `suncode-tool`. Its registry accepts owned custom provider/model identifiers and trusted `Arc<dyn LlmProvider>` implementations. Core implements the credential resolver and DTO conversion boundary.

SDK startup acquires the runtime lock, opens the database, performs recovery, and exposes named in-process methods plus live event subscriptions. There is no client-facing listener, HTTP authentication token, endpoint discovery record, or standalone runtime binary. Session context is built from timestamp-ordered `session_message` user/assistant/thinking rows plus transient tool-role messages derived from succeeded `session_tool_use` results; streaming and lifecycle events are not stored as a duplicate journal. Provider-reported usage updates the cumulative `session_turn` projection, and the named session-usage method returns the sum across turns without estimating missing provider usage. Each provider request is stored in `session_call`, including independently nullable provider HTTP request and response-object identifiers when reported; each tool request/result is stored in `session_tool_use`, and normalized provider traces remain available through the existing SDK methods. Trace summaries contain every session turn and its calls; call detail joins correlated readable messages and tool uses. OpenAI-compatible cache-read, cache-miss, cache-write, and reasoning usage is normalized and retained on the call when reported. The session snapshot retains its flat message compatibility projection and adds correlated conversation turns containing normalized messages and tool uses so clients can rebuild process timelines without opening SQLite. Lagged clients receive `resync.required` and reload that normalized snapshot.

Provider integration is Rust-owned. Core loads enabled rows from `llm_model_provider` and `llm_model`, selects the known `suncode-llm` adapter named by `adapter_type`, and passes owned model descriptors to the registry. The current persisted adapter is `openai`; custom providers therefore need an OpenAI-compatible endpoint unless another adapter is added to the LLM package and runtime dispatch. Provider API keys are loaded from `llm_model_provider.api_key` or explicit non-interactive environment overrides only. Context construction uses persisted `context_tokens` and `auto_compact_tokens`.
Configuration is stored in one table and resolves global, project, and session values in that order. When no model is supplied for a new session or turn, core uses the project's effective `default_model` setting and falls back to the default seeded model only when no configured value exists. The project-only `tool_call_limit` is an integer from 1 through 256 and defaults to 64. Core snapshots it at turn admission and rejects an entire provider-returned tool batch before policy or execution when accepting the batch would exceed the limit.

Projects may register additional read-only source dependencies. Their canonical roots remain in Rust-owned `project_dependency` rows, while SDK clients receive only stable dependency IDs and display names. Directory browsing is shallow, bounded to 500 entries, ignores symlinks, and is loaded on demand. Agent `read`, `glob`, and `grep` calls accept `dependency:<id>/...` and return paths with that alias intact; all mutation, process, Git, and checkpoint operations remain scoped to the main project.

The model-facing tool registry exposes exactly `read`, `glob`, `grep`, `write`, `edit`, `bash`, and `webfetch`. The OpenCode-compatible `bash` tool requires `command` and accepts optional `timeout` in milliseconds (positive, maximum 600000) and `workdir`; it uses Windows PowerShell on Windows and POSIX `/bin/sh` on macOS and Linux. `webfetch` requires an HTTP(S) URL and accepts optional `format` (`text`, `markdown`, or `html`, default Markdown) and seconds-based `timeout` (default 30, maximum 120). Core validates those arguments before requesting network approval, and the operations boundary validates them again. Redirects are limited to the approved host and port or a standard HTTP-to-HTTPS upgrade. Textual responses are bounded to 5 MiB, decoded using BOM or declared charset, converted from HTML where requested, and limited to a 64 KiB model preview with the complete converted result stored as a managed artifact. Binary and image content is rejected because the current model tool-result contract has no attachment channel. Windows child processes use `CREATE_NO_WINDOW` so desktop execution does not allocate or flash a console window. Process execution remains approval-gated, uses a filtered environment, keeps its working directory inside the opened project, continuously drains output streams, retains a bounded tail preview, and exposes oversized output through a complete artifact. Turn cancellation propagates into the process runner, which terminates the Unix process group or Windows process tree before returning. Recoverable argument failures (`invalid_arguments` and malformed tool arguments) are recorded as failed tool results and fed back to the model so the same turn can regenerate a call; non-recoverable authorization, approval, and runtime failures still terminate the turn. Each provider request receives host context containing the target OS, architecture, shell dialect, path style, and stable session-start timestamp. Retired operation names fail closed and are no longer executable.

Approval decisions are `deny`, `allow_once`, and `allow_session`. `allow_session` updates the pending approval and session-scoped `configuration.full_control=true` in one database transaction. Policy reads that boolean for every call and allows known project-write, process, network, and destructive-write risks without another approval while it is enabled. Full Control never authorizes an unknown tool and does not bypass argument translation, canonical paths, dependency or URL restrictions, audited dispatch, checkpoints, or cancellation. Writing `false` through the SDK settings boundary disables it for subsequent calls.
